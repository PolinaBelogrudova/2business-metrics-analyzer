# Архитектура Business Metrics Analyzer

## 1. Обзор системы
BMA — веб-приложение для автоматизации расчёта KPI и формирования отчётов торговой компании (ООО "Ритейл-Аналитика"). 
Границы системы: аутентификация, импорт данных о продажах (CRM/1С), расчёт KPI (выручка, средний чек, конверсия, рентабельность), визуализация на дашборде, экспорт в Excel, управление пользователями.

## 2. Архитектурные драйверы

| ID | Драйвер | Тип | Влияние на архитектуру |
|---|---|---|---|
| AD-01 | Время загрузки дашборда < 3 секунд (NFR-01) | NFR | Кэширование агрегатов в Redis, предрасчёт KPI, оптимизация запросов к БД |
| AD-02 | Разграничение прав доступа (NFR-03, FR-05) | NFR | Модуль аутентификации, JWT-токены, RBAC (роли: директор, аналитик, менеджер, администратор) |
| AD-03 | Автоматическая загрузка данных из CRM/1С (FR-03, CN-03) | Функц. | Выделение сервиса импорта, паттерн Adapter для интеграции с внешними API |
| AD-04 | Запуск MVP через 2 месяца (CN-02, CN-01) | Бизнес | Выбор монолитной архитектуры, отказ от микросервисов на старте |
| AD-05 | Экспорт отчётов в Excel (FR-04) | Функц. | Выделение сервиса отчётов, паттерн Factory для генерации файлов |
| AD-06 | Доступность 99.5% (NFR-02) | NFR | Контейнеризация (Docker), возможность горизонтального масштабирования |
| AD-07 | Единый источник данных (I-04, P-04) | Бизнес | Централизованная реляционная БД (PostgreSQL) |

## 3. Выбранный архитектурный стиль

**Слоистый монолит с элементами Clean Architecture.**

**Обоснование:**
1. **Сроки и бюджет:** Согласно ограничениям CN-01 и CN-02, у нас 2 месяца на MVP и ограниченный бюджет. Микросервисы потребовали бы настройки сложной инфраструктуры (API Gateway, Service Discovery, распределенные транзакции), что нереально в эти сроки.
2. **Команда:** Команда небольшая (3-4 человека), разделение на отдельные микросервисы привело бы к избыточной коммуникации.
3. **Изоляция логики:** Элементы Clean Architecture позволяют отделить бизнес-логику (расчёт KPI, валидация данных) от инфраструктуры (БД, внешние API). Это упрощает написание Unit-тестов.
4. **Путь к масштабированию:** Архитектура позволяет при росте нагрузки выделить «Сервис импорта» или «Сервис отчётов» в отдельные приложения без переписывания ядра.

## 7. Технологический стек
Python 3.10+, FastAPI, SQLAlchemy, PostgreSQL, Redis, Docker, pandas, openpyxl, JWT, MinIO/S3.

## 8. Ограничения и компромиссы
- Монолит ограничивает независимое масштабирование сервисов — компенсируется горизонтальным масштабированием контейнера API.
- Redis-кэш вводит eventual consistency для дашбордов (TTL 5–10 мин).
- Синхронный импорт больших файлов может блокировать воркер — вынесен в фоновые задачи.

## 9. План развития архитектуры
1. Выделение сервиса отчётов в отдельный микросервис.
2. Выделение сервиса импорта с очередью (RabbitMQ/Kafka).
3. Введение API Gateway при появлении внешних потребителей API.
